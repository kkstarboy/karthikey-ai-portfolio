  • Owner status: no design-system, engineering, accessibility, product, content, data, privacy, or security owner was supplied.

Component: CMP-01 Financial summary surface

  • Purpose: Present scoped financial total, comparison/status, and available next actions without implying unsupported certainty.
  • Anatomy: period/status label; primary amount; comparison qualifier; data freshness/help; action group; optional explainable insight link.
  • Variants/sizes: mobile sample only; compact/wide/loading/partial/stale/error variants missing.
  • States: default, loading, empty, partial, stale, unauthorized, error, long/extreme values; only static default exists.
  • Tokens: observed custom gradient, 20px radius, 22px padding, local shadow; not approved.
  • Behavior: no card-level action; each action has explicit name/result; data status remains visible.
  • Content rules: exact period/currency/scope/freshness/comparison basis; no ambiguous “this month” when context is lost.
  • Accessibility: semantic heading/grouping, reading order, sufficient composite contrast, no color/arrow-only change meaning.
  • Responsive rules: preserve amount/period/status association; wrap actions; never truncate a material value without accessible full value.
  • Implementation notes: Candidate only; resolve OQ-02–06.

Component: CMP-02 Financial data row

  • Purpose: Associate a category/merchant label, context, amount/status, and optional authorized action.
  • Anatomy: leading approved icon/marker; primary label; secondary metadata; amount; status/comparison; optional disclosure/action.
  • Variants/sizes: category, transaction, recurring, selectable, read-only, unavailable; architecture unresolved.
  • States: default, focus, selected/current, pending/refund/reversal/duplicate, disabled/unavailable, loading, error, long/localized/extreme.
  • Tokens: sample 42px leading slot, 12px gap/padding, 14px radius; observed only.
  • Behavior: whole-row target only when entire row has one action; avoid nested conflicting controls; explicit unavailable reason.
  • Content rules: preserve merchant/category/date/status/value relationship; wrap labels; approved locale/currency/negative notation.
  • Accessibility: semantic list/list item, accessible action name, programmatic selected/current/status, no icon/color-only meaning.
  • Responsive rules: maintain reading order and amount association; do not hide financial status at narrow widths.
  • Implementation notes: Validate whether existing current-app list/table components already cover this need.

Component: CMP-03 Financial action sheet

  • Purpose: Review and perform a sensitive category/budget/preference action with explicit before/after, cancellation, and authoritative result.
  • Anatomy: dialog title; context; instructions; field/choice group; validation/permission status; review summary; cancel/close; primary action; result/recovery.
  • Variants/sizes: mobile sheet vs platform dialog only after platform decision.
  • States: open, default, focus, validation, pending, success, failure, unknown, offline, conflict, unauthorized, cancelled.
  • Tokens: sample scrim/sheet/radii are observed only; no production token.
  • Behavior: focus enters heading/first meaningful control, is contained, Escape/back and visible cancel do not save, focus returns, duplicate submit blocked, prior authoritative state remains until confirmed.
  • Content rules: state exact effect/scope/future behavior; never use simulated “saved” as production copy.
  • Accessibility: native/library dialog and field/choice semantics; error summary/association; announced status; inert background; no visual-only selection.
  • Responsive rules: avoid clipped keyboard/input; preserve actions and error content; support zoom/reflow.
  • Implementation notes: Blocked by data/API/permission/idempotency and accessibility component decisions.

Component: CMP-04 Explainable data visualization

  • Purpose: Present trend/pattern with source/scope and a structured non-visual equivalent.
  • Anatomy: title; period/scope/freshness; visualization; units/legend where needed; explanation/limitations; table/list alternative; action/control.
  • Variants/sizes: compact summary, detail, no comparison, list/table alternative.
  • States: loading, empty, partial, stale, unavailable, error, extreme/localized, reduced motion.
  • Tokens: no approved data-viz/color/motion tokens.
  • Behavior: inspection does not depend on hover; any animation is supplementary and interruptible.
  • Content rules: qualify inference, calculation, missing data, baseline, and uncertainty.
  • Accessibility: structured equivalent; programmatic label; color/pattern not sole distinction; zoom/reflow and contrast.
  • Responsive rules: preserve labels/values; choose list/table rather than unreadable compression.
  • Implementation notes: Blocked by data/insight rules and user/accessibility validation.

Component: CMP-05 Financial status/result

  • Purpose: Communicate authoritative operation state and safe next action.
  • Anatomy: state label; exact affected item/action; persistence/effective state; timestamp/request reference if approved; retry/cancel/help/navigation.
  • Variants/sizes: inline, page result, persistent banner; transient toast only as supplemental.
  • States: pending, success, confirmed failure, unknown/timeout, partial, cancelled, conflict, offline.
  • Tokens: semantic status tokens missing; never color-only.
  • Behavior: durable for consequential actions; live announcement without repeated noise; no auto-dismiss as sole feedback.
  • Content rules: do not claim success before authoritative confirmation; state prior/effective result and recovery.
  • Accessibility: status role chosen by urgency, focus only when needed, text/icon redundancy, sufficient time.
  • Responsive rules: no overlap with focused controls/sticky navigation; reflow long messages/actions.
  • Implementation notes: Requires API/idempotency/status/cancellation contract.

4. Behavior rules

  1. Use native or authoritative library components before creating a new component.
  2. Treat every financial read/mutation as scoped by authorization, data freshness, and authoritative state.
  3. Do not infer missing loading, error, permission, timeout, cancellation, conflict, or recovery behavior from a default sample.
  4. Use one semantic target for a wholly clickable row; separate and label multiple actions.
  5. For asynchronous actions, prevent duplicate submits and preserve the prior authoritative value until confirmation.
  6. A dialog/sheet must provide visible dismissal, focus containment/return, programmatic state, errors, and responsive keyboard/reflow behavior.
  7. Animation cannot be the only feedback and cannot delay or obscure task completion.
  8. Any implementation deviation or local override requires versioned owner decision and downstream documentation update.

All rules except direct sample observations are Inferred/LOW requirement candidates pending product/engineering/accessibility/risk review.
