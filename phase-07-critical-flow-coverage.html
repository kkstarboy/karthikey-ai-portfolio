Critical Flow Coverage — Prototype Readiness

Scope, evidence, and criticality method

This artifact evaluates whether the available clickable prototype covers critical tasks from realistic entry through alternate, failure, recovery, cancellation, and confirmation outcomes.

  • Prototype asset assessed: Output/visual-design/smart-expense-tracker.html, created as a provisional two-screen visual sample before Phase 07.
  • Authoritative flow inputs: Phase 04 F-01–F-06; Phase 06 wireframes/annotations; G06 record.
  • Asset status: Readable and locally interactive, but not updated to the full Phase 06 screen/state contract.
  • No evidence of: Representative users, pilot participants, task outcomes, current backend behavior, technical feasibility, privacy/security approval, or accessibility conformance.

Criticality is provisional because frequency/reach are unknown:

  • Critical: High user/business harm, core-value dependence, sensitive/irreversible action, or essential recovery.
  • High: Material value/risk but can be excluded from the immediate narrow test with disclosure.
  • Deferred: Outside the current prototype decision.

All classifications are Inferred/LOW pending product, research, risk, and engineering owners.

2. Prototype path definitions

CF-01 — Review spending

  • User and trigger: Provisional candidate opens the sample; real parent-app entry/auth context is absent.
  • Criticality rationale: Core BRD goal and potential financial misunderstanding.
  • Entry state: Static sample overview with pre-populated BRD-format example data.
  • Main path: Overview → Food & Dining row → detail → Back → overview.
  • Alternate/error paths: None simulated.
  • Recovery: Back navigation only.
  • Success confirmation: None; reaching detail does not prove comprehension.
  • Prototype coverage: Partial.
  • Known gap/risk: Cannot test data status, explanation, empty/partial/stale/error, guided alternative, privacy, or task outcome.

CF-02 — Correct category

  • User and trigger: User notices a possibly wrong category.
  • Entry state: Detail contains an Edit category control.
  • Main path: Missing; activation only reports that rule approval is required.
  • Alternate/error/recovery: Missing.
  • Success confirmation: Missing.
  • Prototype coverage: Missing.
  • Known gap/risk: A critical recovery task cannot be tested.

CF-03 — Set budget

  • User and trigger: User activates Set a budget from overview.
  • Entry state: Static overview.
  • Main path: Open dialog → choose one of three simulated amounts → Save → toast.
  • Alternate/error paths: Dialog close/Escape is supported; validation, permission, existing budget, offline, timeout, and failure are missing.
  • Recovery: Close without saving.
  • Success confirmation: Toast only; no persistent or effective notification state.
  • Prototype coverage: Partial.
  • Known gap/risk: Unrealistically constrained values and fake successful persistence may change task difficulty.

CF-04 — Review recurring

  • Entry/main/alternate/recovery/confirmation: Missing.
  • Prototype coverage: Missing.

CF-05 — Export/share

  • Entry state: Overview Share Summary control.
  • Main path: Missing; activation reports preview only.
  • Alternate/error/recovery/confirmation: Missing.
  • Prototype coverage: Missing.
  • Known gap/risk: Cannot test a sensitive action without authorization, file, cancel, and no-share outcomes.

CF-06 — Unusual pattern

  • Entry state: Static insight content.
  • Main/alternate/recovery/confirmation: Missing.
  • Prototype coverage: Missing.

6. Readiness decision

Decision: NOT READY for representative-user usability testing of the declared critical flows.

The clickable asset is suitable only for an internal interaction pilot of:

  • overview-to-category navigation and back behavior;
  • budget-dialog open/select/close/toast mechanics;
  • keyboard focus and reduced-motion checks already described in the sample notes.

Before external testing, at minimum implement/disclose CF-01 data states, complete CF-02, resolve CF-05 scope or exclude it explicitly, add safe error/cancel paths, label all wizard-of-oz behavior, and pilot accessibility/links. A participant must never be evaluated on a prototype limitation without disclosure.
