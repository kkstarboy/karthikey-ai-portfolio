Interactive Prototype — Limited Pilot Record

1. Prototype scope

Decision and research questions

The current prototype can support only an internal pilot of basic navigation and dialog mechanics. It cannot answer whether users understand spending, recover from category errors, safely export, trust data, or complete all critical flows.

Interactive asset

  • Clickable HTML: Output/visual-design/smart-expense-tracker.html
  • Supporting images: Output/visual-design/screen-01-overview.jpg, screen-02-food-detail.jpg
  • Original notes: Output/visual-design/sample-design-notes.md
  • Asset provenance: Provisional visual sample created before Phase 07; adopted for inspection without claiming alignment to all Phase 06 behavior.
  • Fidelity: Styled two-screen simulation with a budget dialog and status toast. It exceeds mid-fidelity visually in places but remains behaviorally shallow.
  • Access: Local project file only; no external distribution or access-control claim.

All data is static demonstration content based on BRD examples. It is not personal, live, measured, or backend-connected.

2. Interactive prototype

PR-01 — Overview to category detail

  • Research/decision goal: Pilot whether the navigation mechanics and focus transition operate as intended—not whether the IA or content is understood.
  • Entry point: HTML opens on overview; no parent-app/auth/consent context.
  • Covered screens/states: Overview and Food & Dining detail.
  • Interactions simulated: Open category, back to overview, URL query state, focus movement.
  • Data/content: Static BRD-format totals/categories.
  • Known limitations: No data states, period selection, full categories, insight explanation, task confirmation, or real navigation shell.
  • Device/viewport: Responsive browser sample styled as a mobile surface; supported device matrix not defined.
  • Test status: Source inspected; earlier internal browser QA recorded in sample notes. No Phase 07 participant/pilot run.

PR-02 — Budget dialog mechanics

  • Research/decision goal: Pilot open/select/close/status mechanics.
  • Entry point: Set a budget from overview.
  • Covered screens/states: Dialog open, one of three static values selected, close/Escape, success toast.
  • Interactions simulated: Selection, save, toast, focus return.
  • Data/content: ₹5,000/₹6,000/₹8,000 static choices; no input validation or current-spend logic.
  • Known limitations: Save always appears successful; no persistence, existing budget, notification permission, threshold behavior, error, offline, timeout, or effective-state confirmation.
  • Device/viewport: Same local browser sample.
  • Test status: Limited internal mechanics only; not suitable for task-result measurement.

PR-03 — Non-functional preview controls

  • Controls: Share Summary, See all, Insights, Budgets, Edit category, and more options.
  • Behavior: Toasts disclose preview/limitation instead of presenting fake interactions.
  • Testing restriction: These controls must be explained as non-functional before any session and cannot be used to evaluate discoverability, success, or error recovery.

4. Prototype instructions

  1. Open Output/visual-design/smart-expense-tracker.html in a local browser.
  2. Confirm the overview is visible and disclose that all values are static BRD examples.
  3. Activate Food & Dining to open detail; use Back to return.
  4. Activate Set a budget; select a preset value; Save to display the simulated toast. Close/Escape should return focus.
  5. Treat all toast-only controls as non-functional and do not assign tasks that depend on them.
  6. Do not enter or display real financial or personal data.
  7. Stop if a path differs from the documented simulation; record it as a prototype defect, not participant failure.

Pilot script before any sharing

  • Check every interactive control by keyboard and pointer.
  • Check focus entry/return, visible focus, Escape, live-status announcement, and reduced-motion preference.
  • Check mobile/narrow, text zoom/reflow, and long-label behavior.
  • Check that non-functional controls are disclosed and cannot be mistaken for complete flows.
  • Record asset hash/version and any defect before a session.

No Phase 07 pilot result is claimed in this artifact.

5. Known limitations

  • The asset predates the official Phase 06 wireframes and is not flow-complete.
  • No authentic parent app, authentication, authorization, consent, data status, backend, API, analytics, security, performance, or persistence exists.
  • Only CF-01 and CF-03 have partial simulations; CF-02/04/05/06 are missing.
  • Static content may reduce task difficulty and cannot test data variability, uncertainty, localization, or real account contexts.
  • Visual styling may bias preference despite unresolved structural questions.
  • No representative user, product/dev, accessibility, privacy/security, or legal review occurred.
  • The sample’s earlier browser QA is an internal mechanics check, not usability evidence or Phase 07 pilot evidence.

6. Test-readiness checklist

  • Prototype asset and scope are named.
  • Static data, simulated success, non-functional controls, and production differences are disclosed.
  • Available navigation/dialog interactions can be internally inspected.
  • Device/accessibility considerations and safe pilot steps are documented.
  • Critical category-correction flow implemented end-to-end.
  • Loading, empty, partial, stale, permission, validation, error, timeout, offline, cancellation, and recovery states implemented.
  • Export scope either implemented safely or explicitly excluded from the approved test plan.
  • Product/dev/accessibility/privacy review completed.
  • Prototype pilot completed and defects resolved.
